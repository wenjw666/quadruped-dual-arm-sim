# C1200 外设、辅域与相机接入盘点

## 1. 实机结论

本次检查对象是 `192.168.1.100`，设备树报告为 `BST C1200 CDCU RC12`。当前 Linux 主域为 8 核 Cortex-A78AE，在线 CPU 为 `0-7`。系统没有出现 `/sys/class/remoteproc/remote*`、独立辅域 CPU 集群或可直接登录的第二个 Linux 域。

资料中的“AI 辅域”在当前设备上没有以独立 Linux/remoteproc 设备暴露。可见的是 NPU、4 个 DSP/LWNN 相关运行时、IPC/消息盒子和 SCMI 依赖：

- 设备树节点：`bst-npu@50020000`、`bst-dsp@51000000`、`bst_lwnn@51000000`、`bst-ipc`、`bst-mbox`、`bst-msgbox`、`safety`、`scmi`。
- 设备节点：`/dev/bstn0`、`/dev/bstdsp`、`/dev/bst_lwnn`、`/dev/bstipc0d`、`/dev/ipc_msgbox0`。
- 固件：`bstn_dsp_rtos*.rbf`、`bst_lwnn_dsp0..3_rt*.rbf`、DSP RPC firmware 和 ISP IPC firmware。
- 没有发现面向应用的 AI 辅域命令行、远程登录入口或公开消息协议。

因此，辅域“存在于架构/固件资源划分中”这一点可以确认；“能够像 Linux 主域一样直接控制”目前不能确认。更准确的理解是：AI 辅域由 SBL/固件/SCMI/IPC 管理，Linux 应用只能通过厂商提供的封装或驱动间接使用。

## 2. 当前可见外设接口

下表区分“Linux 当前可见”和“产品/原理图声明”。产品规格中的数量不等于当前 Linux 域已经开放的数量。

| 类别 | 当前实机可见 | 产品/原理图信息 | 使用判断 |
|---|---|---|---|
| CPU | 8× A78AE，CPU 0–7 在线 | 模组规格 8 核 | 可用于预处理、Tokenizer、语言解码和控制程序 |
| NPU/BSNN | `/dev/bstn0`、`libbsnn.so.6.1.1`、`libbsnn.so.7.1.0` | 70 TOPS | YOLO 已跑通；SmolVLM 需要先分段编译验证 |
| DSP/LWNN | `/dev/bstdsp`、`/dev/bst_lwnn`；4 路 LWNN DSP 固件 | 异构 DSP/MCU 资源 | 可通过 LWNN/BSNN 运行已编译模型；没有发现通用 DSP 任务控制 API |
| IPC/消息盒子 | `/dev/bstipc0d`、`/dev/ipc_msgbox0`、`/sys/kernel/bst-ipc`、IPC DMA heap | 多域共享内存/消息通道 | 由驱动和厂商协议使用；不应自行写消息格式 |
| UART | `/dev/ttyS0`–`/dev/ttyS7`，共 8 个 | 产品资料 10× UART；Debug/串口 B/C 等由载板映射 | 运行时可见 8 路；串口功能需按 DT/载板丝印确认 |
| I2C | `/dev/i2c-4`、`5`、`6`、`7`、`11`；已枚举多个从设备 | 产品资料 6× I2C | 可用于已定义的传感器/相机控制；不要对未知地址写寄存器 |
| I3C | DT 中有 3 个 I3C 控制器，但未发现对应用户态 `/dev/i3c*` | 产品资料 2× I3C | 当前不能按普通 Linux 用户接口直接使用 |
| SPI | `/dev/spidev0.0`、`/dev/spidev1.0` | 产品资料 2× SPI | 两路已开放；片选、电压和设备协议需查原理图 |
| GPIO | `/dev/gpiochip0`–`/dev/gpiochip11`；sysfs 显示多个 GPIO bank | 产品资料 GPIOs | 可见 GPIO 字符设备，但当前用户缺少 `gpioinfo`；按 gpiochip/DT 复核后再操作 |
| PWM | `/sys/class/pwm/pwmchip0` 1 路，`pwmchip1` 8 路 | 产品资料 8× PWM | 目前暴露约 9 路；通道用途需查 DT/载板 |
| ADC | 未发现 `/dev/iio:device*` | 产品资料 5× ADC，且 RC12 有 Safety/外设 ADC | 很可能由 Safety/MCU 域或专用驱动管理，当前 Linux 无通用 IIO 入口 |
| CAN | `can0`–`can3`，当前均 DOWN/STOPPED；SocketCAN 工具存在 | 产品资料 1 路 Safety + 8 路常规 CAN-FD | 当前 Linux 只看到 4 路；业务 CAN ID/波特率/安全协议仍缺失 |
| 以太网 | `eth0`–`eth5`、`xgmac0`；当前 `eth3=192.168.1.100/24` 有链路 | RC12 有多路 1/2.5GbE 与 10GbE/TSN | `eth3` 用于当前 SSH；其他物理口需接线后确认 |
| USB | 4 个 USB 总线；ADB Google 设备、USB Hub、键鼠可见 | DX-5000-D 有 USB-A/USB-C/ADB/Debug | UVC 相机可作为最短路径，但会走 USB/CPU/ISP 兼容路径 |
| PCIe | 发现两个 PCI bridge：`0000:00:00.0`、`0001:10:00.0`，暂无 endpoint | PCIe Gen4 1×4 或 2×2 | 可扩展 NVMe/采集卡，但当前没有插入设备证据 |
| GPU/显示 | `/dev/mali0`、`/dev/dri/card0` | Mali-G78AE，500+ GFLOPS；HDMI/DSI/DP | 可用于图像处理/语言解码候选，但需单独做 GPU 软件栈验证 |
| CSI/ISP | `/dev/video4`–`7`、`20`–`23`；`video60`–`63` 为 CSI TX；`bst-isp-video` | 3× MIPI CSI-2、12 lanes | ISP 视频节点已注册，但当前没有有效 GMSL 视频链路 |
| 存储 | `sda` 40G，根分区约 39.6G；当前约 28G 可用 | 资料标称 64GB UFS 3.1 | 当前系统可用空间足以放置小型模型和测试数据；完整 VLM 仍需实际峰值测量 |

## 3. 相机链路的实机状态

当前启动日志提供了明确证据：

- `MAX96712` GMSL2 hub 位于 `i2c-7` 地址 `0x29`。
- CSI 接收端 `53100000.csi` 已配置为 4 lanes、2500 Mbps，MIPI channel 0–3 已连接到驱动图。
- ISP 使用 `bst-isp`，并启用了 IPC 模式。
- ISP 已注册 `/dev/video4`–`/dev/video7` 和 `/dev/video20`–`/dev/video23`。
- 4 个 GMSL channel 在启动时都报告 `not linked`，没有检测到实际摄像头视频链路。
- `/dev/video4` 的 V4L2 信息为 `isp-channel-4-views-video`，`Video input: camera: ok`，但当前格式为 `0×0`，说明节点存在而有效帧格式尚未建立。
- 启动日志同时报告了 `bst,maxim-deser-hub` 的 EEPROM DT 属性缺失提示；这不一定阻止视频，但说明相机设备树描述还没有完全匹配当前硬件。

原理图进一步给出：

- RC12 载板使用 `MAX96712GTB` 作为 GMSL 到 CSI 的解串 Hub。
- 载板给 GMSL Camera 0–2 提供独立的 P12V 供电分支。
- CSI0/CSI1/CSI2 高速差分信号连接到 Aura 模组；当前运行日志实际激活的是 `MIPI 1 / 53100000.csi`。
- 原理图对 MAX96712 的 I2C 配置地址标注为 0x29，和实机 `7-0029` 一致。

## 4. 相机接入建议

### 推荐路径：先接 GMSL2 Camera 0

对于后续 SmolVLM，优先使用 RC12 原生 GMSL2 路径，因为它更接近板端 ISP/CSI 的预期数据流：

1. 选用与 BSP/设备树支持匹配的 GMSL2 摄像头和 serializer。载板端已经是 MAX96712，摄像头侧 serializer、sensor 型号、I2C 地址和 CSI 数据格式必须和 BSP 配置一致。
2. 先只接 `Camera 0`，不要同时接多路，降低链路、地址和供电问题的定位复杂度。
3. 使用 RC12 对应的 GMSL 相机连接器和 P12V POC 供电；确认摄像头电压、电流、同轴/屏蔽和连接器方向。不要在 POC 已供电时再外接一组未经确认的电源。
4. 接入后先只做链路和视频验证：查看 `dmesg` 中 `is_gmsl2_video_connected()` 是否由 `not linked` 变为 linked，确认 `v4l2-ctl --list-devices`，再查询 `/dev/video4` 或对应 channel 的格式。
5. 先用低风险固定格式，例如 1280×720 或 1920×1080、YUV/NV12；确认能稳定抓帧后，再选择 RGB/ISP 输出供 SmolVLM 预处理。
6. 如果 sensor 未被识别，优先补齐设备树中的 sensor、serializer、alias、lane、pixel format、clock 和 power/reset 描述；不要先改 NPU 或跨域配置。

### 快速验证路径：USB UVC Camera

如果目标是尽快开始 SmolVLM 图像输入验证，可以先接一只标准 UVC USB 相机：

- 优点：不依赖 MAX96712/GMSL serializer 和设备树，验证速度快。
- 代价：可能走 USB + V4L2/CPU 路径，带宽、延迟和颜色格式转换不代表最终 GMSL 性能。
- 建议：先使用 `v4l2-ctl`/GStreamer 验证帧率和格式，再把单帧送给 SmolVLM；模型验证稳定后再切换到 GMSL/ISP。

### 不建议一开始采用的路径：直接 MIPI Sensor

直接 MIPI CSI sensor 只有在载板实际引出对应 CSI lane、供电、I2C、reset、clock 和 BSP sensor driver 都匹配时才可用。当前 RC12 的主要摄像头通路已明确采用 MAX96712 GMSL Hub，直接接裸 MIPI sensor 需要额外的设备树和驱动适配，适合作为后续工作。

### 与 SmolVLM 的数据流建议

```text
GMSL Camera
  -> MAX96712
  -> MIPI CSI / ISP
  -> V4L2 video node
  -> NV12/YUV 或 RGB 帧
  -> CPU/GPU/HWCV resize + normalize
  -> SmolVLM Vision Encoder
```

初期建议固定一个 224/384/512 等模型所需的输入尺寸，先离线图片、再 USB UVC、最后 GMSL 实时流，逐级隔离模型问题和相机问题。

## 5. SmolVLM 工具链和资源就绪性

### 已经满足的条件

- C1200 板端 Linux、BSNN/NPU 驱动、DSP 固件和 OpenCV 可用。
- 现有 YOLO 样例已证明 BSTNNX → C1200 模型包 → BSNN C++ Runtime 的闭环可运行。
- 主机资料中存在 `bsnn_tools_docker_8.3.1.tar.gz`、C1200 编译 YAML、校准流程和 C++ BSNN 头文件。
- 板端有约 28G 根分区可用空间，足以放置中小型实验模型和结果。
- 板端 GPU `/dev/mali0` 和 CPU 资源可用于预处理、Tokenizer、语言解码候选。

这已经足以立即开始 SmolVLM 的**主机侧拆分、ONNX 导出、算子盘点和视觉编码器编译试验**。

### 还不满足直接部署完整 SmolVLM 的条件

当前仍缺少：

- 确切的 SmolVLM 变体、权重、配置、Processor、Tokenizer 和任务定义。
- Vision Encoder、projector、Language Decoder 的拆分导出实现。
- C1200 编译器对 Attention、LayerNorm、GELU/SiLU、RoPE、Gather/Embedding、动态 shape 和 KV-cache 的实测结果。
- 自回归逐 token 循环和 KV-cache 的板端运行方案。
- 语言 Decoder 的 CPU/GPU fallback 方案。
- 主机 PyTorch/ONNX Runtime 参考结果和量化校准数据。
- Docker 工具链版本、Net-FW、板端 Runtime 6.1.1/7.1.0 与固件版本的匹配确认。

因此结论是：**现在可以开始研究和编译 SmolVLM 的视觉子图，但还不能承诺一次性编译完整端到端 SmolVLM。** 最稳妥的路径是：

1. 获取确切 SmolVLM 模型包和 processor。
2. 在 x86 主机导出固定 shape 的 Vision Encoder。
3. 在主机完成 PyTorch 与 ONNX Runtime 数值对齐。
4. 用现有 BSTNNX Docker 先编译 Vision Encoder，优先 INT8 或编译器支持的混合精度。
5. 将编译产物放到 C1200，比较视觉特征输出。
6. Projector 和 Decoder 先在 CPU/GPU 跑通，再逐层评估 NPU 化。

## 6. 当前不应执行的操作

以下操作会影响启动配置或多域资源，本轮没有执行：

- `hwcv-cross-domain-on/off`
- `isp-use-ipc`
- 修改 `/boot` 或 DTB/overlay
- 修改 `/sys/kernel/bstn/*`、`/sys/kernel/bst-ipc/*`
- 直接写 `switch1_xpcs_tool` 寄存器
- 未取得 CAN 协议前启用 CAN 并发送业务帧

这些接口需要厂商协议、root 权限、回滚方案和重启窗口，不能作为普通的 SmolVLM 试验步骤。
