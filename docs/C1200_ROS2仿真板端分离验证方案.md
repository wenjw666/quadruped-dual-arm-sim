# C1200 ROS2 仿真与板端功能节点分离验证方案

目标是让本机继续运行 MuJoCo/RL/控制仿真，让 C1200 运行待验证的视觉、SmolVLM、感知和后续功能节点；两侧通过局域网交换 ROS2 消息。这样测到的是板端节点的真实 CPU、内存、图像吞吐和推理延迟，同时保留仿真的传感器和机器人反馈。

## 推荐边界

```text
本机 qda-dev / MuJoCo
  发布：/clock /camera/image_raw /camera/depth/image_raw
        /joint_states /odom /imu /scan /tf /tf_static
  接收：/smolvlm/response /perception/labels /perception/pick_pose
        /cmd_vel_nav 或经安全门控的测试输出
             │  CycloneDDS + ROS_DOMAIN_ID=8 + Ethernet
             ▼
C1200
  c1200_smolvlm、C1200 YOLO、后续 qda_perception/brain/gateway
  只发布语义结果或经过限幅的测试命令，不直接替代 MuJoCo
```

第一阶段只让板端发布 `/smolvlm/response` 和诊断信息，不把动作送回仿真控制器。第二阶段才允许回送一个明确命名的 `/board/test_cmd_vel`，由本机的 `qda_command_mux` 或独立测试门控转成 `/cmd_vel`。这样可以测时延和消息契约，又不会让实验节点绕过安全仲裁。

## 网络和 DDS 参数

当前实机地址为 C1200 `192.168.1.100`，本机物理网卡为 `192.168.1.101/24`。MuJoCo 脚本会按后端自动使用 Domain 8（Gazebo 使用 Domain 7），而 `compose.yaml` 默认写的是 7；分离测试必须显式把 MuJoCo 容器设为 Domain 8，不能依赖 Compose 默认值。

本机容器：

```powershell
$env:QDA_ROS_DOMAIN_ID = "8"
docker exec -e ROS_DOMAIN_ID=8 `
  -e RMW_IMPLEMENTATION=rmw_cyclonedds_cpp `
  -e CYCLONEDDS_URI=file:///ws/docker/cyclonedds_c1200.xml `
  qda-dev bash -lc 'source /opt/ros/humble/setup.bash; source /ws/install/setup.bash; ros2 topic list'
```

板端：

```bash
source /opt/ros/humble/setup.bash
source /userdata/smolvlm/ros_ws/install/setup.bash
export ROS_DOMAIN_ID=8
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export CYCLONEDDS_URI=file:///userdata/ros_net/cyclonedds_c1200_board.xml
```

`docker/cyclonedds_c1200.xml` 是可选的静态 peer 配置，默认工程不会加载它。第一次联调应先验证容器能访问 `192.168.1.100`；Docker Desktop 的 Linux VM/桥接网络可能阻断 DDS UDP 或 multicast。如果容器内不能直接发现板端，优先使用 Docker 的 host/mirrored networking；仍不通时再部署 `domain_bridge`/Zenoh relay，而不是修改 C1200 或关闭防火墙。

板端匹配文件的关键内容是把 peer 写成本机 `192.168.1.101`，并保留 `AllowMulticast=false`。不要把 `eth3` 作为板端 XML 中的固定接口名复制到容器，容器内网卡名通常不同。

## 启动顺序

1. 启动 C1200 的 SmolVLM 服务和 ROS 节点：

   ```bash
   bash /userdata/smolvlm/c1200_start_smolvlm.sh
   ```

2. 在本机启动 MuJoCo，但先关闭真实执行动作：

   ```powershell
   .\scripts\windows\run_sim.ps1 -Backend mujoco -MotionMode rl -Headless -NoRviz -Background
   ```

3. 两侧分别检查发现：

   ```bash
   ros2 topic list | grep -E 'camera|odom|joint_states|smolvlm'
   ros2 topic echo /smolvlm/status --once
   ```

4. 先用 320×240、5 FPS 的仿真 RGB 图像验证板端输入；稳定后再升到 640×480。原始 `bgr8` 带宽约为：

   | 输入 | 原始带宽 |
   |---|---:|
   | 320×240×3×5 FPS | 0.92 MB/s |
   | 640×480×3×10 FPS | 9.22 MB/s |
   | 三路 640×480×3×10 FPS | 27.65 MB/s |

   千兆网足够单路或少量多路原始图像，但 JPEG/`CompressedImage` 更适合把网络抖动和 CPU 复制开销控制住。SmolVLM 首版只订阅一张 RGB 图像即可，Depth、IMU 和状态先保持低频。

## 节点拆分建议

| 节点 | 运行位置 | 输入 | 输出 | 第一阶段 |
|---|---|---|---|---|
| `/qda_mujoco` | 本机 | 仿真状态、控制 | 相机、odom、joint、IMU、scan | 保留 |
| `camera_topic_bridge` | 本机或板端 | 仿真图像/真实相机 | `/smolvlm/image` | 本机发仿真图像 |
| `/c1200_smolvlm` | C1200 | RGB、prompt | `/smolvlm/response` | 已可用 |
| C1200 YOLO runner | C1200 | RGB | labels/debug | 下一步 |
| `qda_perception` | C1200 | RGB-D/YOLO | pick pose/labels | 先 dry-run |
| `/local_brain` | C1200 或本机 | 反馈、VLM | 受限技能提案 | 后续迁移 |
| Nav2/MoveIt/RL | 本机仿真 | 板端语义或测试命令 | 仿真动作 | 先保留本机 |

`/clock` 是否跨网发布要根据仿真节点需要决定。板端视觉节点不需要仿真时钟，可以使用墙钟；需要 `use_sim_time` 的板端算法才订阅 `/clock`。跨网时应避免让多个参与者发布 `/clock`、`/tf_static` 或同名控制话题。

## 验收指标

每轮测试记录：

- 板端 CPU 总占用、每核占用、RSS、线程数和温度；
- 图像接收 FPS、图像时间戳年龄、DDS 丢包和序列号；
- SmolVLM prompt、视觉编码、生成和端到端延迟；
- `/smolvlm/response` 与仿真帧序号的一致性；
- ROS2 节点重启后是否能自动恢复发现；
- 板端异常、网络断开或推理超时是否只产生安全的空结果。

建议用三档输入：单路 320×240@5 FPS、单路 640×480@10 FPS、三路 640×480@10 FPS。SmolVLM 当前约 5.6 秒/完整图像请求，因此它适合事件触发语义理解，不适合直接承担 20–50 Hz 控制环；高频控制仍由仿真侧或专用实时节点完成。

## 回退方案

如果 Windows Docker 的 DDS UDP 不能直通 `192.168.1.100`，保留同一套消息契约，改为：本机录制 `rosbag2` → 通过 TCP/HTTP/Zenoh 发送图像和状态 → 板端发布同名 ROS2 输入话题。这样可以继续验证板端模型和节点性能，但不再是完整 DDS 实时闭环；正式实物方案再切回局域网 DDS 或板端直接接相机。
