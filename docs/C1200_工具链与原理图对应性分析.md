# C1200 工具链、外设参数与 RC12 原理图对应性分析

## 1. 先给结论

当前板子可以和资料中的 RC12 原理图对应上，而且对应关系较强：

- 实机设备树型号是 `BST C1200 CDCU RC12`。
- 软件启动日志加载了 C1200 CSI、ISP、MAX96712 GMSL Hub 和 4-lane MIPI 接收端。
- RC12 原理图中正好有 MAX96712、GMSL Camera 0–2、CSI0/CSI1/CSI2、I2C 控制和相机 P12V 供电。
- 实机检测到 `i2c-7/7-0029`，也就是 MAX96712 的 0x29 地址，与原理图一致。
- 实机 CSI 日志显示 4 lanes、2500 Mbps，和 Aura/NX-5000 的 CSI 能力和板端配置相符。

这能确认“当前设备是这套 RC12/C1200 硬件平台”。它不能单独证明原理图上每一个连接器、每一根线或每一个外设电源都已经接入；物理连接仍需要看板卡丝印、线束和万用表/示波器测量。

## 2. 板上各接口分别是什么

### 2.1 NPU / BSNN

实机节点是 `/dev/bstn0`，用户态库包括 `libbsnn.so.6.1.1` 和 `libbsnn.so.7.1.0`。NPU 是专门执行神经网络张量计算的硬件，当前资料和 YOLO 样例主要走 INT8、固定 shape、静态 DAG。

它适合执行卷积、部分矩阵计算和经过 BSTNNX 编译的网络子图；它不是一个可以直接运行 PyTorch、Transformers 或 Python 模型的通用处理器。YOLO 已经证明了“编译模型包 + BSNN Runtime + C++ API”这条路径。

关键参数和约束：

- 产品资料给出 AI 性能 70 TOPS。
- YOLO 实际输入是 640×640×3、UINT8、WHD。
- C1200 模型输出是 INT8，板端用量化 scale 做反量化。
- 输出 tensor 有 pitch，对齐后通道数可能大于逻辑通道数。
- 模型必须是 `.lib`、`.meta`、`weights.bin`、辅助权重和 RBF 等 BSNN 产物，不能把 ONNX 直接复制到板端当成 NPU 模型。

### 2.2 DSP / LWNN

实机有 `/dev/bstdsp` 和 `/dev/bst_lwnn`，并加载了 `bst_lwnn_dsp0..3_rt` 等 4 路 DSP 固件。LWNN/BSNN 运行时可以把适合的网络或部分任务交给 DSP/NPU 侧执行。

它不是“AI 辅域的 Linux 系统”。当前没有看到可以 SSH 进去的 DSP 用户态系统，也没有看到公开的通用 DSP 任务调度 API。能否利用某个 DSP 能力，要看 BSNN/LWNN 的模型类型、编译器产物和厂商 API。

### 2.3 UART

当前 Linux 设备节点为 `/dev/ttyS0` 到 `/dev/ttyS7`，共 8 路。资料中的调试串口统一参数是 115200、8 数据位、1 停止位、无校验、无流控。

用途通常包括：Linux 控制台、Safety/SBL 日志、外设 MCU、传感器或执行器通信。`ttyS0` 到 `ttyS7` 与载板连接器的物理编号不能仅凭编号推断，必须按照 DT、原理图和串口枚举顺序确认。当前 SSH 进入的是 Linux 主域，不是每个 UART 对应的其他域。

### 2.4 I2C

当前可见：`/dev/i2c-4`、`/dev/i2c-5`、`/dev/i2c-6`、`/dev/i2c-7`、`/dev/i2c-11`。I2C 是低速控制总线，适合配置摄像头 serializer/deserializer、传感器、PMIC、GPIO 扩展器、风扇控制器等。

实机已经发现多个从设备，例如：

- `7-0029`：MAX96712 GMSL Hub。
- `7-0054` 到 `7-0057`：相机 sensor/alias 相关配置地址。
- `7-0055`、`7-0056`、`7-0057` 等地址必须根据具体 sensor 和 DT 判断，不能直接写寄存器。

I2C 读写改变的是硬件状态，尤其是相机、PMIC 和时钟设备。调试时先使用 `i2cdetect -l`、sysfs 和驱动日志确认设备，再使用厂商驱动或专用工具。

### 2.5 SPI

当前开放的是 `/dev/spidev0.0` 和 `/dev/spidev1.0`。SPI 速度快于 I2C，通常用于 IMU、外部 ADC、Flash、显示或其他实时外设。`spidev` 只说明 Linux 暴露了总线设备，不说明片选、电压、时钟极性、最大频率和数据协议；这些必须查 RC12/RC12_EXT 原理图和具体器件手册。

### 2.6 GPIO

当前有 `/dev/gpiochip0` 到 `/dev/gpiochip11`，说明多个 GPIO bank 已注册。GPIO 可以控制复位、使能、中断、相机 PWDNB、风扇、继电器、LED 和执行器信号。

GPIO chip 编号不是原理图上的 GPIO 编号。真正使用时要建立：

```text
物理引脚 -> GPIO controller -> line offset -> DT signal name -> 电平/方向/复用
```

当前系统没有安装 `gpioinfo`，所以只能确认 GPIO bank 存在，不能仅靠 `/dev/gpiochipN` 得到安全的逐线名称。相机 PWDNB、RESET、FSYNC 等信号必须优先使用现有驱动控制。

### 2.7 PWM

当前有两个 PWM 控制器：一个暴露 1 路，另一个暴露 8 路。可用于风扇转速、背光、执行器、蜂鸣器或周期性控制信号。PWM 的频率、占空比和极性决定外设行为，不能在不知道负载的情况下随便导出并改变。

### 2.8 ADC

产品资料给出 5 路 ADC，RC12 原理图中也有 ADC/Safety 相关信号，但当前没有发现 `/dev/iio:device*` 这样的 Linux IIO 用户态设备。更可能的情况是部分 ADC 由 Safety/MCU 域或专用驱动管理。

因此，“产品有 ADC”不等于“当前 Linux 用户可以直接读取 ADC”。需要厂商提供 IIO 驱动、SCMI 接口或 Safety 命令协议。

### 2.9 CAN

当前系统有 `can0`、`can1`、`can2`、`can3`，SocketCAN 工具也存在，例如 `cansend`、`candump`、`canfdtest`。但实机四路都是 `DOWN/STOPPED`。

产品资料写的是 1 路 Safety CAN-FD + 8 路常规 CAN-FD；这和 Linux 当前只看到 4 路不矛盾，因为其他 CAN 控制器可能由其他域、Safety 固件或不同 DT variant 管理。

启用 CAN 前必须知道：

- nominal bitrate 和 data bitrate；
- CAN-FD 是否启用；
- 终端电阻和收发器连接；
- 报文 ID、周期、字节序、信号缩放；
- Safety 报文的计数器、CRC、超时和状态机。

没有这些信息时只能做接口探测，不能向真实执行器发送业务报文。

### 2.10 以太网

当前可见 `eth0` 到 `eth5` 以及 `xgmac0`。实机 `eth3` 有 `192.168.1.100/24`，SSH 就是通过它连接的；其他接口显示为无 carrier 或未接线。

原理图/产品资料提供多路 1/2.5GbE 和 10GbE/TSN 能力，但 Linux 网卡名称与物理 RJ45 顺序不能直接等同。要逐一确认物理口，应在接线后查看 carrier、MAC、速率和交换芯片端口。

### 2.11 USB

实机识别到：

- Google ADB 设备；
- USB 3 Hub；
- Logitech 键盘/无线接收器。

USB 适合快速接入 UVC 摄像头、RealSense、U 盘和调试设备。USB 设备由主机 CPU 和 USB 控制器管理，链路不会直接进入 RC12 的 MAX96712/CSI/ISP 路径。

### 2.12 PCIe

当前只发现两个 PCI bridge，没有发现 endpoint。PCIe 可以扩展 NVMe、采集卡、无线模块或其他协处理器，但当前没有证据表明已经插入并枚举了 PCIe 设备。

### 2.13 GPU / 显示

当前有 `/dev/mali0` 和 `/dev/dri/card0`。GPU 适合做图像格式转换、部分张量计算、显示合成或语言模型 fallback，但是否有可用的 OpenCL/Vulkan/特定推理后端，需要单独查询软件栈；仅有 `/dev/mali0` 不能证明 Transformers 或 ONNX Runtime 会自动使用它。

### 2.14 CSI / ISP

当前有：

- `/dev/video4` 到 `/dev/video7`；
- `/dev/video20` 到 `/dev/video23`；
- `/dev/video60` 到 `/dev/video63`，对应 CSI TX。

实机日志显示 CSI 接收端 `53100000.csi` 使用 4 lanes、2500 Mbps，ISP 使用 IPC 模式并注册了视频节点。但 GMSL 四路当前都是 `not linked`，所以视频节点存在不代表已经有有效图像帧。

## 3. RealSense 与 GMSL/ISP 的区别

### 3.1 GMSL/ISP 相机

GMSL 相机链路是：

```text
GMSL Camera + Serializer
    -> 同轴/屏蔽双绞线
    -> RC12 MAX96712 Deserializer
    -> MIPI CSI
    -> C1200 ISP
    -> V4L2 video node
```

这种路径直接使用 RC12 的相机供电、MAX96712、MIPI CSI 和 ISP，适合机器人长期运行、多相机同步、低延迟和稳定帧率。摄像头必须满足：

- 与 MAX96712/BSP 支持的 GMSL2 serializer 匹配；
- sensor 型号有对应 Linux driver 或 DT 配置；
- sensor 地址、serializer alias、lane 数、pixel format、clock、reset/PWDNB 与 DT 一致；
- 使用正确的 POC 电压、同轴线和连接器；
- 先接 Camera 0 验证，再扩展多路。

### 3.2 RealSense 相机

RealSense D4xx 系列通常走 USB 3.x。典型链路是：

```text
RealSense
    -> USB 3.x
    -> Linux xHCI / V4L2 / HID
    -> librealsense 或 V4L2
    -> RGB/Depth/IR 帧
    -> SmolVLM 预处理
```

它不走 MAX96712、MIPI CSI 或 RC12 ISP。RealSense 的 RGB、Depth、IR、IMU 可能分别表现为多个 USB/V4L2/HID 接口，深度处理还可能在相机内部完成。

接入建议：

1. 使用 USB 3.x 口，避免 USB 2 Hub；
2. 先确认 `lsusb`、`/dev/video*`、`udevadm` 和 USB 带宽；
3. 在板端确认对应架构的 `librealsense`/ROS2 驱动是否已有；
4. 初期只取 RGB 图像给 SmolVLM，Depth/IMU 另行处理；
5. 如果使用高分辨率 RGB + Depth + IR，要测 USB 带宽、CPU 占用和内存拷贝；
6. 最终产品若要求多相机、确定性低延迟和 ISP 零拷贝，GMSL/CSI 通常比 RealSense USB 更合适。

因此，RealSense 适合快速验证 SmolVLM 的摄像头输入；GMSL/ISP 更适合最终机器人产品链路。RealSense 能否直接运行，还取决于具体型号和板端 aarch64 的 librealsense/ROS2 支持，不能只根据 USB 枚举成功就认为深度流可用。

## 4. 现有 YOLO 工具链如何工作

### 阶段 1：模型训练或准备

资料中的 `train/` 是主机侧工程，基于修改后的 Ultralytics 8.1.34。模型配置将普通 Conv 默认激活设为 `nn.ReLU()`，原因是减少 SiLU 在目标编译器和 NPU 上的风险。

YOLO 的检测后处理没有放进模型主干：DFL、边框解码、置信度处理、NMS 和绘图由板端 C++ 完成。

### 阶段 2：导出 ONNX

浮点模型通过 `train/yolov8.py --export` 导出 ONNX。C1200 编译前的关键要求是：

- 固定输入尺寸和 batch；
- 模型图尽量静态；
- 不把难以编译的后处理放入图中；
- 明确输入预处理和输出张量布局；
- 在主机用 PyTorch/ONNX Runtime 对齐输出。

YOLO 的 C1200 输入约定是 BGR→RGB、缩放 1/256、640×640、UINT8/WHD。

### 阶段 3：生成校准数据

主机从代表性图片生成 `compiler/calibrate_data/`。校准数据用于估计每层激活范围，决定 INT8 量化 scale。校准数据不只是“随便几张图片”，应覆盖实际摄像头的亮度、颜色、场景和目标尺度。

### 阶段 4：BSTNNX Docker 编译

工具链运行在主机 Docker 中，不运行在板端。C1200 配置核心是：

```yaml
device_engine: C1200
orig_model_format: onnx
net_batch_size: 1
enable_static_dag: true
image_process_config:
  source_image_format: BGR
  target_image_format: RGB
  scale: [0.00390625, 0.00390625, 0.00390625]
```

`bstnnx_run` 的主要阶段是：

```text
100 预处理
200 图优化
250 模型固化/权重准备
300 INT8 量化
400 图切分
500 Section Binding
600 代码生成
700 代码编译
1100 硬件测试
1500 Userland 产物
```

输出包括：

- `quant_model.onnx`：主机侧 INT8 精度验证模型；
- `1500_UserlandStage/`：板端需要的模型包和运行配置；
- `.meta`：输入输出 tensor、layout、pitch、dtype、量化 scale 等元数据；
- `.lib`：模型描述/执行库；
- `weights.bin`、加密权重和 RBF：运行时权重和硬件相关产物。

### 阶段 5：推送到板端

资料给出的方式是 ADB 推送，也可以用 SCP：

```bash
adb push Deploy/prebuild /userdata
# 或
scp -r Deploy/prebuild bst@192.168.1.100:/userdata/
```

部署目录至少要保持模型、输入、参考输出、应用和脚本的相对关系。板端还必须有兼容的 BSNN Runtime、驱动、DSP/Net-FW 和系统固件。

### 阶段 6：板端 C++ 推理

当前 YOLO 程序的执行过程是：

```text
OpenCV 读图
  -> resize/letterbox/BGR->RGB/归一化
  -> WHD UINT8 输入 buffer
  -> bsnn_model_load()
  -> bsnn_model_query() 查询 tensor 属性
  -> NPU 推理
  -> 读取 INT8 输出和 dequant scale
  -> CPU DFL/box decode/NMS
  -> OpenCV 绘图
```

所以当前工具链不是“板端直接执行 ONNX”，而是“主机编译成 BSNN 专有模型包，板端通过 C/C++ Runtime 调用”。

## 5. SmolVLM 完整部署方案的准备方式

当前可以开始，但需要按子图拆分：

```text
Vision Encoder -> Projector -> Language Decoder -> Tokenizer/采样
```

### 第一阶段：Vision Encoder

先用固定图像尺寸、固定 batch 导出 Vision Encoder，主机侧完成 PyTorch 与 ONNX Runtime 数值对齐，然后用 BSTNNX 编译到 C1200。这个阶段最接近 YOLO 的成功模式。

### 第二阶段：Projector

单独验证 Linear/MatMul、Reshape、Transpose、LayerNorm 等算子。如果编译器不支持，就放在 CPU/GPU。

### 第三阶段：Language Decoder

先在 CPU/GPU 跑通 tokenizer、prompt、逐 token 解码、停止条件和 KV-cache。之后再测试固定序列、单步 decoder block 是否适合 NPU。

当前已经具备：板端、NPU、DSP、GPU、CPU、BSNN Runtime、BSTNNX Docker 和 YOLO 参考链路。

当前还缺：确切 SmolVLM checkpoint/config/processor/tokenizer、主机导出脚本、算子覆盖实测、动态 shape/KV-cache 方案、Decoder fallback，以及工具链与板端 Runtime/Net-FW 的版本匹配记录。

## 6. 工具链版本需要先锁定

资料和实机存在版本差异：

- 文档写 `bsnn_tools_v7.0.0`；
- 本地归档名称是 `bsnn_tools_docker_8.3.1.tar.gz`；
- 板端存在 BSNN 6.1.1 和 7.1.0 两套库；
- 启动日志显示 BSTN/BSTNPU 驱动版本为 `V1.5.0.3...C1200`；
- DSP RTOS 固件文件带有 5.2.2 版本标记。

开始 SmolVLM 编译前，应在 Docker 中记录 `bstnnx_run --help`/版本信息，在板端记录实际加载的 `libbsnn`、Net-FW 和固件版本，并把它们固定成一组可复现组合。
