# C1200 联合调试与资源性能记录

日期：2026-10-30  
分支：`codex/c1200-yolo-smolvlm-adaptation`

## 网络现状

主机当前有线地址为 `192.168.1.101/24`，C1200 有线地址为 `192.168.1.100/24`；主机无线地址为 `10.186.150.150/24`。板端当前只有 `192.168.1.0/24` 的直连路由，所以 ROS2 调试应优先固定在有线口，不能把无线地址直接填入板端 peer。

已在主机用户级 `.wslconfig` 启用 WSL mirrored networking。WSL 已同时看到 `192.168.1.101`、无线地址和 Docker 相关接口，SSH/TCP 以及板端 UDP 报文均可到达主机。板端抓包能够看到主机向 `9410`–`9426` 发送 CycloneDDS 报文，主机也能看到板端向 `192.168.1.101` 返回报文，说明物理链路和防火墙路径已经打通。

Docker Desktop 仍然把容器放在自己的 Linux VM/bridge 网络中。其 UDP 映射会把端口发布到 loopback 的随机主机端口，不能稳定地把 CycloneDDS participant 的地址和端口宣告为 `192.168.1.101`。因此当前 ROS2 图尚未完成跨主机 topic 匹配；问题已从“网络不通”缩小为 Docker Desktop 的 DDS participant 端口/NAT 配置。新增的 `cyclonedds_c1200_nat.xml` 和 `cyclonedds_c1200_board_nat.xml` 已加入固定 `ParticipantIndex=0` 与 `ManySocketsMode=false`，用于让端口集合变得可预测。下一步应在 WSL mirrored 的本地 Docker daemon 中运行仿真容器，或改用 Zenoh/domain bridge，避免继续映射数百个 UDP 端口。

配置文件现已进一步固定 `Discovery/ParticipantIndex=0`、`ManySocketsMode=false`，使 Domain 8 的基础单播端口可预测。CycloneDDS 文档说明，关闭多 participant socket 后端口集合更适合防火墙/NAT；但 Docker Desktop 仍需要把容器宣告的 `192.168.1.101` 正确映射到物理网卡，因此仍建议优先使用 WSL mirrored 的本地 Docker daemon或 Zenoh relay。

最小 `std_msgs/String` 反向验证已经成功：Docker 容器映射 UDP `9410–9426` 后，C1200 可以收到 `/lan_test`。完整仿真不能直接套同一静态配置，因为 MuJoCo 会启动多个独立 participant；因此新增 `ros2_c1200_topic_bridge.py`，让仿真保持默认 multicast，多 participant 的 relay 单独使用静态 Ethernet profile，并将 `/camera/image_raw` 转发为 `/c1200/camera/image_raw`。当前仿真节点组已正常启动，relay 能看到仿真图像并重新发布；板端 participant 的反向 endpoint 发现仍在继续排查，暂未宣称完整图像链路已闭环。

## SmolVLM CPU 性能

使用板端常驻 CPU `llama-server`、同一张 MuJoCo 输出图像、`max_tokens=64`：

- 连续两次 HTTP 请求延迟为 `8978.8 ms` 和 `4157.6 ms`，平均 `6568.2 ms`。
- 双请求并发延迟为 `8.68 s` 和 `14.99 s`；当前服务使用 `--parallel 1`，请求会排队。
- 并发期间 llama-server CPU 峰值约 `665%`（约 6.7 个核心），RSS 约 `1.03 GiB`，温度最高约 `39°C`。
- 通过 ROS2 `/smolvlm/image` 和 `/smolvlm/prompt` 完成一次完整节点测试，返回 `image_seq=5`，端到端延迟 `24632.1 ms`；此时 `vlm_node` RSS 约 `80 MiB`，llama-server RSS 约 `1.03 GiB`，CPU 峰值约 `573%`。

## SmolVLM Vulkan/Mali 性能

使用 `/userdata/smolvlm/build-vulkan/bin/llama-server`、修正后的临时 ICD JSON 和 `Mali-G78AE`：

- `--list-devices` 能枚举 `Vulkan0: Mali-G78AE (12787 MiB)`。
- 冷请求延迟 `53295.0 ms`，热缓存请求为 `2937.6 ms` 和 `2944.5 ms`。
- 热请求生成速度约 `22 token/s`，服务 RSS 约 `1.0 GiB`，线程数 22。
- GPU 推理期间 CPU 峰值约 `95%`（约 1 个核心），温度最高约 `36°C`。
- 双请求并发在 `--parallel 1` 下串行，延迟约 `50.5 s` 和 `53.4 s`，说明当前 GPU 后端应作为常驻 warm service 使用，不能按每帧冷启动。

## 视觉 projector 冷启动优化

默认的 llama.cpp 空文本 warmup 不会执行图像 projector。进一步测试发现，请求内容如果按“文本→图像”排列，提示词变化会破坏视觉前缀缓存；改成“图像→文本”后可复用图像 token：

- Vulkan 服务重启后，第一次真实图像请求约 `48.7 s`，主要耗时在视觉 projector/shader 初始化；
- 使用相同图像做一次 `max_tokens=1` 的启动预热后，再换一条文本请求，耗时约 `5.6 s`，其中 prompt 处理约 `2.7 s`、生成 64 token 约 `2.8 s`；
- CPU 服务启动预热约 `4.2 s`，之后图像→文本请求分别约 `0.46 s`（10 token）和 `4.32 s`（64 token）。

仓库中的 `c1200_smolvlm_warmup.py` 和 `c1200_start_smolvlm.sh` 已固化该策略。启动脚本默认使用 `/userdata/smolvlm/test_mujoco_overview.jpg` 预热，可用 `C1200_SMOLVLM_WARMUP=0` 关闭，或通过 `C1200_SMOLVLM_WARMUP_IMAGE` 指定实机相机样图。ROS 节点也已改为图像先于文本，后续不同任务提示词可以共享视觉前缀。

## 能力判断

板端内存余量充足，单路 SmolVLM 服务可以长期驻留；CPU 路径在单请求下可用，但并发会迅速占满多个核心，需由 ROS 节点做请求门控和丢帧。Vulkan 路径已经能使用 Mali，热缓存时明显降低 CPU 占用。采用图像前置和启动预热后，冷启动代价被隔离到服务启动阶段，实际请求不再承担约 50 秒的首次 projector 初始化；`parallel=1` 仍会让并发请求排队，因此建议保持单路请求、预热常驻，并把图像频率限制在单请求完成速度以内。

资源采样脚本为 `scripts/c1200_board_resource_probe.py`，ROS2 网络探针为 `scripts/ros2_lan_probe.py`。板端日志和原始 JSON 采样保存在 `/tmp/c1200_*`，可在下一轮网络通道打通后复用同一套测试。
